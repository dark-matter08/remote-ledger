# v0.2.0 — job profiles, and autopilot

Two features. One reshapes the data model; the other chains work that already exists.
Written before any code, so the decisions are visible and can be argued with.

---

## Feature 1 — job profiles

### The problem

There is exactly one search profile, held as three rows in `settings`:

```
profile_field     profile_location     profile_stack
```

Everything downstream reads them: the crawl prompt, the relevance vocabulary in
`app/fields.ts`, the board-side feed filters, the scorer. So a second line of work means
overwriting all three and losing the first — the "discard and start over" that prompted
this.

`resume_profiles` is already multi-row (`id`, `name`, `is_default`), so the résumé side
of the idea half-exists. Nothing else does.

### What a profile owns

**Decided: its own boards and companies too.** The fullest separation of the three
options considered.

| | Belongs to a profile | Stays shared |
|---|---|---|
| Field, location, stack | ✅ | |
| Search prompt | ✅ | |
| Boards and tracked companies | ✅ | |
| Jobs found | ✅ (its own copies) | |
| Résumé profile it tailors from | ✅ (a pointer) | |
| Knowledge base, answer bank | | ✅ |
| AI runner, keys, budget settings | | ✅ |
| Email accounts | | ✅ |

The knowledge base stays shared deliberately: it is a record of what you have actually
done, and that does not change because you are applying for a different kind of role.
What changes is which parts of it get used.

### Schema

```sql
CREATE TABLE IF NOT EXISTS profiles (
    id          TEXT PRIMARY KEY,           -- slug: 'engineering', 'design'
    name        TEXT NOT NULL,
    field       TEXT NOT NULL,              -- app/fields.ts id
    location    TEXT NOT NULL DEFAULT '',
    stack       TEXT NOT NULL DEFAULT '',
    prompt      TEXT,                       -- null = the templated default
    resume_profile_id TEXT REFERENCES resume_profiles(id) ON DELETE SET NULL,
    active      INTEGER NOT NULL DEFAULT 1, -- inactive = skipped by crawls
    sort_order  INTEGER NOT NULL DEFAULT 0,
    created_at  TEXT NOT NULL,
    updated_at  TEXT NOT NULL
);
```

`companies` gains `profile_id TEXT NOT NULL` — that table already holds boards as well
as companies (`kind: company | board`), so one column scopes both.

### Jobs: separate copies per profile

**Decided: keep them fully separate.** A posting found under two profiles becomes two
rows, each with its own stage, notes and history.

This has a consequence worth stating plainly, because it partly reverses work done in
September: `jobs.id` is the primary key and is the slug `company--role`, and the
`url_key` dedup added on top of it is global. Separate copies means **the dedup key
becomes per-profile** — the same posting must be allowed to exist twice, once per
profile, while still never duplicating *within* one profile.

```sql
ALTER TABLE jobs ADD COLUMN profile_id TEXT NOT NULL DEFAULT 'default';
-- id stays the primary key, but is now namespaced: '<profile>--<company>--<role>'
CREATE UNIQUE INDEX idx_jobs_profile_urlkey ON jobs(profile_id, url_key)
    WHERE url_key IS NOT NULL;
```

`upsertJobs` keeps its current shape — prefer `url_key`, fall back to slug, fold twins
on sight — but every lookup gains `AND profile_id = ?`. The tests written for that
behaviour should be extended rather than replaced: the same two-postings-one-job case,
asserted once within a profile and once across two, where it must *not* fold.

The cost of this choice is honest to state: applying to a job under one profile leaves
its twin under another sitting at "to-apply" forever. Mitigation is a note on the board
when a `url_key` exists under another profile — a badge, not a merge.

### Crawling for several profiles

**Decided: every profile each run, with the existing budget divided between them.**

The crawl already carries a budget in two modes (`crawl_mode` = `time` | `count`), and
the agent is told to count its own web actions because it cannot perceive time. That
budget is currently spent on one search. It becomes the total:

- **time mode** — `timeoutMin` split across active profiles, floored at a usable
  minimum. Below that floor, the run degrades to round-robin rather than giving every
  profile a budget too small to return anything, and says so in the log.
- **count mode** — `want` divided the same way.

Each profile is a separate agent invocation with its own prompt and its own
`FetchLedger`, run sequentially. One profile failing must not abort the others; the run
records a per-profile result and the `crawl_runs` row summarises.

`crawl_runs` gains `profile_id TEXT` — null for a run that covered everything, set for a
manual single-profile crawl. The crawl page groups its log by profile.

### Migration

167 jobs, 66 companies, 36 applications, 12 résumé profiles. Small enough to do in one
transaction with no batching.

1. Create `profiles`. Insert one row, `id = 'default'`, from the three existing settings
   rows, named after the current field.
2. `profile_id = 'default'` on every existing job and company.
3. Leave `profile_field` / `profile_location` / `profile_stack` in `settings` for one
   release, written through from the default profile, so a half-updated install cannot
   read nothing. Remove in v0.3.
4. Job ids are **not** rewritten. Existing ids stay bare; only new profiles namespace
   theirs. Rewriting 167 primary keys would cascade into `applications`,
   `resume_versions` and `apply_session_jobs` for no user-visible gain.

### UI

- **Settings → Profiles** — the list, create, edit, delete, set active. Deleting asks
  what to do with its jobs (keep, or remove with them).
- **A profile switcher in the Shell header**, next to the nav. Board, inbox, analytics
  and funnel scope to it. "All profiles" is a valid selection and the default.
- **Setup wizard** — step 3 creates the first profile instead of writing three settings.
  An existing install skips this; the migration already made one.
- **The board** shows a profile badge when "All profiles" is selected.

## Feature 2 — autopilot

### What exists

The Guided Application tab already has the five steps, and its `done` map is the
sequence:

| Step | Intent | Done when |
|---|---|---|
| 1 Match | `match` | a stored match exists |
| 2 Build from KB | `kb-build` | `built_for_job_id` set, or a version exists |
| 3 Tailor résumé | `tailor` | a résumé version exists |
| 4 Cover letter | `cover` | a cover version exists |
| 5 Apply | `assist-apply` | stage moved off `saved` |

Plus `draft-answers` for the questions, and `scripts/apply-chrome.mjs` for the browser.

Autopilot does not need new capability. It needs an **engine that runs the existing
steps in order, survives one of them failing, and reports.**

### Shape

**Decided: one job now, batch later** — so the engine is a queue from the first commit,
with a single-job UI on top.

```
app/services/autopilot.server.ts

  runAutopilot(jobId, { from, to, signal }) → AsyncIterable<AutopilotEvent>
```

Steps are declared as data, not a hardcoded chain:

```ts
const STEPS = [
  { id: 'match',   needs: [],                run: …, skipIf: hasMatch },
  { id: 'build',   needs: ['match'],         run: …, skipIf: builtForJob },
  { id: 'tailor',  needs: ['build'],         run: …, skipIf: hasResume },
  { id: 'cover',   needs: ['tailor'],        run: …, skipIf: hasCover },
  { id: 'form',    needs: [],                run: detectForm },
  { id: 'answers', needs: ['form','tailor'], run: draftAnswers },
];
```

`skipIf` matters: re-running autopilot on a job you part-did by hand must not redo paid
work. Every step is resumable and idempotent.

**Failure stops the run.** These steps cost money and each feeds the next — a cover
letter written from a résumé that failed to tailor is worth less than nothing. The
partial result is kept, the failed step is named, and a Continue button resumes from
there.

**Cancellation** reuses the crawl's pattern, and the lesson from it: the controller is
dropped from the map the moment abort is called, not when the tail unwinds, so a
stopped run stops blocking immediately.

### Persistence — no new table

The first draft of this plan proposed an `autopilot_runs` table. Checking the schema
first showed that would have been redundant: `crawl_runs` is already the generic record
of "something ran and logged", and its `type` column is carrying `match`, `tailor`,
`cover`, `prep`, `answers` and `kb-gap` today alongside the actual crawls.

So autopilot opens a `crawl_runs` row with `type='autopilot'` and writes through the
existing `crawlLog(runId, kind, text)`. Three things fall out of that for free:

- The crawl page's log shell renders it with no new component.
- `activeCrawl()` filters `type IN ('find','update','full')` on purpose, so an autopilot
  run does not block a crawl or the scheduler, and a crawl does not block it.
- `loggedTask`, which already wraps the individual steps, is the same mechanism — so
  each step keeps logging exactly as it does when run by hand.

The one addition is a `job_id TEXT` column on `crawl_runs`, so a run can be found from
the posting it belongs to. It is null for crawls, which is what it already effectively
is.

### The ending

Autopilot stops **before** anything is submitted. It never was going to do otherwise —
"no auto-submit ever" is in the README and the mission — and the two buttons are the
whole point of stopping there:

- **Open and fill myself** — opens the apply URL in your default browser. Answers and
  file paths are on screen to copy.
- **Open and autofill** — `scripts/apply-chrome.mjs`, which fills what it is confident
  about and leaves the rest. Demographic and EEO fields are never touched, which
  `prefill.server.ts` already enforces and which stays enforced.

### Batch, later

The queue is built now and driven with one job. Adding batch is then: select on the
board, enqueue N, run sequentially, one card per job. No engine change — which is the
reason for building it queue-shaped while it only ever holds one.

## Feature 3 — export and import

### The problem

Everything lives in `data/jobs.db` on one machine, which is the point. It also means a
new laptop starts empty, and the only way across today is to copy a directory by hand
and hope the paths line up.

### What travels

One file: `remote-ledger-<date>.json.gz`. Plain JSON so it can be read and checked
before it is trusted, gzipped because a few hundred postings of description text
compresses to almost nothing.

| Included | Left out, deliberately |
|---|---|
| Profiles, and their boards and companies | **API keys and email passwords** |
| Jobs, applications, events | The master key (`data/.master.key`) |
| Résumé profiles and versions | Rendered PDFs |
| Knowledge base, answer bank | `llm_calls` — a cost ledger for one machine |
| Answered application questions | Crawl and autopilot logs |
| Settings that are preferences | Backups |

**Secrets never leave the machine, even into a file you asked for.** `secrets` is
skipped in full. An export names what it omitted, so the first thing the new machine
tells you is which keys to re-enter — rather than looking like it worked and failing on
the first crawl.

PDFs are omitted because they are derived: `version/:vid/resume.pdf` renders them on
demand from the version rows, which do travel. Nothing is lost that cannot be remade.

### Import

Two modes, chosen on the way in:

- **Merge** — add what is not already here, keyed on the natural key of each table.
  Anything already present is left alone, so an import can be repeated safely.
- **Replace** — wipe the scopes being imported first. Backs up before it does, using
  `backup.server.ts`, which already exists for exactly this class of moment.

Import refuses a file from a **newer schema than it understands** rather than guessing
at columns it has never seen. Same version, or older with a documented upgrade, or it
declines and says why.

### Per-profile, too

The same machinery narrowed: export one profile with its boards, companies and jobs but
not the others. That is the shape someone wants when they are handing a search to a
second machine, or splitting one profile off to keep.

## Order of work

1. `profiles` table, migration, CRUD, Settings → Profiles. No behaviour change yet;
   the default profile reads exactly as today.
2. Scope `companies` and `jobs` to a profile. Extend the dedup tests to cover
   within-profile and across-profile.
3. Crawl for every active profile with the divided budget.
4. Profile switcher, board badges, setup wizard step.
5. `autopilot.server.ts`, the queue, the step table, and `job_id` on `crawl_runs`.
6. The Guided Application button, streamed progress, the two endings.
7. Export and import, per-profile and whole-install, with secrets excluded.
8. Docs, CHANGELOG, tag `v0.2.0`.

1–4 ship on their own if 5–7 slip. 5–7 do not depend on 1–4 and could go first if the
autopilot is wanted sooner.

## What could go wrong

- **Cost.** Every profile each run multiplies agent invocations even with a divided
  budget, because there is a fixed prompt cost per invocation. Worth watching on the
  usage page after the first multi-profile run, and worth a hard ceiling if it bites.
- **A budget too thin to work.** Three profiles on a 15-minute crawl leaves five minutes
  each, and the agent needs a few to be useful at all. Hence the floor and the
  round-robin fallback.
- **Two copies of one job.** The chosen model allows it. The badge softens it; it does
  not remove it.
- **Autopilot on a thin knowledge base** produces a weak résumé quickly and expensively.
  It should refuse to start when the KB has nothing for the posting, and say so, rather
  than spend six steps discovering it.
