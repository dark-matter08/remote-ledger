# v0.2.1 — a match score worth gating on, and applying in batches

Planned, not built. Written while v0.2.0 is under review so the reasoning survives the
gap, and so the two open questions get answered before any code is committed to them.

---

## The finding that shapes everything else

**There is no rubric today.** `analyzeMatch` asks the model:

> You assess how well a candidate's resume matches a job. Be concrete and honest.
> Return ONLY JSON: `{ "score": 0, "matched": [...], "missing": [...], "atsKeywords": [...] }`

Nothing anywhere defines what 70 means, or how it differs from 80. The stored matches on
this install read 82 and 68 — but those numbers are not comparable to each other, and
not reliably reproducible for the same job tomorrow.

So a configurable minimum is not a small addition on top of the existing score. **A
threshold on an undefined number is a threshold on noise**, and it would refuse to apply
for jobs on the strength of a figure the model effectively improvised. The rubric is a
precondition for the gate, and has to land first or with it.

## There are already two scores, answering different questions

| | where it comes from | coverage here | cost |
|---|---|---|---|
| `jobs.fit_score` | the crawl, when the posting is scored | **all 215 jobs** | already paid for |
| `match.score` | `analyzeMatch`, per job on demand | **27 jobs** | one model call each |

`fit_score` asks *does this job suit my profile*. `match.score` asks *does my résumé
match this posting*. Only the second is worth gating an application on.

This decides how selection works. A batch cannot be chosen by match score without first
running match against every candidate, which is a paid call each — you would spend the
money to discover which jobs you did not want to spend money on. So:

- **selection** uses `fit_score` and the existing rules — free, already there
- **the gate** uses `match.score` — paid, and only for jobs that reached the session

Two thresholds, not one setting doing both jobs.

## The rubric

Not "return a score" but "score these dimensions, and show your working":

| Dimension | Weight |
|---|---|
| Must-have skills | 40 |
| Seniority and years | 20 |
| Domain familiarity | 15 |
| Location and eligibility | 15 |
| Nice-to-haves | 10 |

The model returns a sub-score **and a quoted justification** per dimension. **The total is
summed in code, not by the model.** Three things follow:

1. The number becomes reproducible, because it is arithmetic over judgements rather than
   one holistic guess.
2. The reader can see *why* it is 62 instead of being told that it is — which is the
   difference between a gate you trust and one you disable.
3. Weights can be retuned without re-running the model against anything.

`MatchAnalysis` gains `dimensions: { key, score, max, evidence }[]` and a
`rubricVersion`. The existing `score`, `matched`, `missing` and `atsKeywords` stay, so
nothing that reads a match today breaks.

## Where the gate sits

Immediately after step 1 of autopilot, before the résumé is tailored.

That is the cheap place to stop: one model call spent rather than four. Below the
threshold, the run halts, keeps the match, and surfaces **Force apply** — which resumes
from step 2, because every step already skips what is done. No new resume machinery.

## Applying in batches

Smaller than it sounds. `ApplyRules` already carries `categories`, `minFit`, `stages`,
`max` and `requireJd`, and a session runner already exists with `draft | assist` modes.

The work is a third mode that calls `runAutopilot(jobId)` for each selected job and
applies the gate per job. This is what the queue shape in `autopilot.server.ts` was for.

**A skipped job must not pause the session.** Skip it, collect it, and report the skipped
set at the end with per-job force-apply. A batch that stops on the third of twelve is a
batch you have to sit and watch, which defeats the point of running one.

## Risks, named before they bite

- **Score drift.** A model change moves the numbers under a threshold set months
  earlier. Storing `rubricVersion` with each score makes that visible rather than
  mysterious; a changed version should invalidate comparisons, not silently survive them.
- **A floor stricter than expected** could quietly stop everything and look like the
  feature is broken. Ship it in **advise mode first**: show what it *would* have blocked,
  for a week, before it blocks anything.
- **Batch cost is real.** Five jobs at roughly six steps each is about thirty model
  calls. The session should estimate and show that before it starts, and honour a
  per-session ceiling.
- **Gaming the gate.** A model asked for a number that decides an outcome can drift
  toward the outcome. Scoring dimensions with quoted evidence is the defence: it is
  harder to inflate a claim you must quote the posting for.

## Open — needs a decision before building

1. **Fixed weights, or editable per profile?** A design search weights domain
   familiarity differently from an engineering one, which argues for per-profile. Against
   it: five more numbers to tune before the feature does anything, and a default that
   nobody changes is a simpler promise.
2. **Force apply — per job only, or also session-level?** Per job is the safe default.
   A session-level "apply to everything you skipped" is convenient and is also exactly
   the button that undoes the point of having a threshold.

## Order of work

1. Rubric in `analyzeMatch`: dimensions, evidence, total summed in code, `rubricVersion`.
2. Show the breakdown on the job page and in the Guided Application match step.
3. `min_match_score` setting, plus advise mode.
4. The gate in autopilot, after step 1, with Force apply.
5. Session mode `autopilot`, per-job gate, skipped set reported at the end.
6. Cost estimate and per-session ceiling.

1–3 are worth having on their own: a match score you can read the reasoning for is
better than one you cannot, whether or not anything is ever gated on it.
